# 行舟影视存储体检（2026-10-11）

> 本文正文是 **2.8.24 改动前的只读体检快照**。后续 2.8.25 的修复状态见文末，不能把正文的缺失项全部当作新版现状。

体检对象：2.8.24 桌面端、本机实际数据目录、正在运行的腾讯云后端、PostgreSQL 与 COS。时间约为北京时间 14:05—14:18。应用运行期间的大小是时点数据，可能继续变化。

本次以体检为主：没有修改业务代码、删除项目或历史版本，没有迁移资料，没有执行数据库维护或对象删除。结论不等于对所有账号、所有离线电脑做过逐项恢复验证。

## 结论

“内容创作者以本地为主、确有协作需要才使用云端”的方向已经基本落实。当前没有发现磁盘即将写满、云端回收站清理任务失效或已匹配的云端图片对象缺失。

需要升级的是存储生命周期：本地资料目录迁移不完整、项目永久删除与附件清理没有贯通、云端数据库删除与 COS 对象删除没有可靠闭环，以及本地整份 JSON 重复保存。不能把所有缓存、备份和生成记录一律当垃圾删除。

## 已验证正常的部分

1. **内容创作者默认本地保存。** 创作编辑通过应用本地状态与 Electron 文件保存；导入、导出走本地文件接口。未发现普通创作编辑自动创建云协作项目或把全体创作项目自动上传 COS 的路径。AI 功能会把本次请求所需文本发送给所选模型服务，这与软件把项目长期保存到协作云端是两件事；第三方模型的数据保留政策不在本次核验范围。
2. **本地七天回收站生效。** 当前策略 `automatic: true, retentionDays: 7`，有 3 个回收条目。启动及运行中每小时检查到期；软件关闭时不会在后台独立执行，下一次启动才清理。云关联导演项目不会误入本地项目回收站。
3. **云端三天回收站任务正常。** `xingzhou-purge.timer` 为 active，上次任务成功退出（状态 0）。数据库有 13 个项目，其中 7 个处于删除恢复期，0 个超过期限仍未清理。相关子表配置级联删除。
4. **更新缓存已有约束。** 当前只剩 2.8.23、2.8.24 两份完整安装包与一个旧下载片段，共 199.25 MiB；原先 4.8 GB 的积累没有继续保持。现行代码保留最近两份完整包、保护活动包并清理匹配的旧缓存。旧式 `.download` 片段不在现行匹配范围，不能据此承诺所有历史格式都自动清理。
5. **云图片缓存不是无限增长。** 原图配置上限 512 MiB，缩略图 128 MiB，均有 30 天未使用规则。回收主要在新增缓存时触发，不是每天独立后台清理；长期不再访问的目录可能继续占用空间。
6. **已匹配的 COS 引用都能找到对象。** 在扫描的协作项目、素材、媒体、消息、版本等数据库文本/JSON 中提取到 792 个对象键，均在对象列表中存在。这里只核对对象存在性，没有下载校验每张图片内容。

## 需要升级的地方

### 1. 优先修复：切换资料目录未完整迁移相关文件

证据：`electron/main.cjs:132` 的 `applyDataDirectory` 只复制主状态、导演状态，并迁移 quick-generation；没有同时迁移 `画布素材`、`analysis-checkpoints`、`art-review-checkpoints`、`director-live-local` 等目录。素材访问协议又限定在当前资料目录内。

影响：切换目录后，旧素材可能仍留在原目录，而当前软件无法按原路径正常访问；分析、核实和协作本地进度也可能读取不到。旧文件并未因此被删除，但容易表现为“内容不见了”。不建议把“修改保存路径”当作完整搬家工具使用。

建议：做完整迁移清单，先复制业务文件及进度、重写受控素材引用、核验文件与数量，再原子切换配置。缓存可以重建，项目和未发布草稿必须迁移。旧目录经核验后再提供清理入口，失败时可回退。

### 2. 云端图片删除缺少可靠的物理清理闭环

证据：`cloud-backend/src/repository-extras.cjs:314`、`:324` 的美术图片删除/清空仅更新数据库；`:386` 的过期项目清理删除项目记录及级联子记录，没有同时排队删除 COS 对象。`cloud-backend/src/collab.cjs:334` 返回成功后也没有执行 COS 删除。

另一条通用媒体删除路径虽然返回签名 DELETE，但客户端 `electron/cloud-media-service.cjs` 忽略网络异常且不校验 HTTP 成功状态，缺少可靠重试。它与美术图片删除不是同一路径。

COS 当前没有生命周期配置（接口返回 `NoSuchLifecycleConfiguration`）。当前扫描有 **137 个 / 199.07 MiB 未匹配引用对象**，其中 **122 个 / 174.79 MiB 已超过七天**。这些只是待核查候选：扫描没有解析 CRDT 二进制内容、其他电脑的未上传草稿，也不能排除正在上传但尚未提交记录的文件，不能直接等同可安全删除量。

建议：业务删除时在数据库同一事务写入对象回收队列，经过恢复期和上传宽限期后，由服务端重新核对活动项目、回收站和应保留历史的引用，再删除对象。失败留记录并重试，成功才结案。不要对整个 `projects/` 设置“文件满七天就删”的生命周期规则。

### 3. 本地永久删除目前主要删除项目 JSON，不贯通附件和进度

证据：`core/projectRecycle.js:45` 的 `purgeRecycledProjects` 移除快照并留下删除标记与审计，没有关联本地素材/进度清理；`electron/analysis-checkpoints.cjs` 只有读取、写入，没有按项目删除接口。导演生成进度虽有底层 remove 接口，但尚缺与项目永久删除统一衔接的清理流程。

影响：项目过期后，其素材、已完成任务原始回复、分析/核实文件可能继续留在磁盘。不能把当前 1.230 GiB 素材全算作残留，因为有效项目、回收站和其他功能可能复用同一个文件。

建议：记录项目—素材—进度的归属和引用；移入回收站时保留，永久清理时只删除“所有有效项目、回收站及受保护版本均不再引用”的受控文件。未发布草稿、下载恢复凭据、未完成任务不能按文件年龄直接删除。保留删除标记，避免旧副本恢复时把已删项目重新带回。

### 4. 本地整份状态重复写入，仍有放大 I/O 的空间

证据：`core/directorPersistence.js:28` 每次保存依次写完整主状态及完整导演项目数组；`src/App.jsx` 创作编辑也使用这套保存器。当前一次完整保存对应约 145 MiB 的两份 JSON 数据，实际写入量随当时内容变化。虽然已有防抖、串行写入和后台序列化，仍然不是“只保存本次修改的项目”。

建议：渐进改为本地项目分文件，或 SQLite 事务存储；内容创作者继续本地保存，编辑哪个项目就写哪个项目，媒体独立存文件，列表只载入摘要。先建立备份、迁移和回退验证，再替换旧格式。无需为解决本地卡顿把普通创作资料转存云端。

### 5. 备份与历史应保留价值，但减少重复

主状态的 `state.pre-creator-v260.backup.json` 是一次性迁移备份，不是滚动备份；导演 `.backup.json` 主要在项目数量减少时更新，不能当作所有最新编辑的连续备份。旧 Local Storage 备份可能包含尚未核对的恢复内容，因此本次保留。

云端现有 11 条导演历史版本，版本表总占用约 3.81 MiB；27 条协作增量，原始增量约 1.12 MiB，目前规模很小。但 `director-live.cjs` 会保存全量 CRDT 状态，并累计增量；活动编辑超过五分钟会建立完整历史检查点，未见独立的增量归档/压缩清理流程。长期持续使用会增长。

建议：本地增加受控的滚动备份和恢复校验；云端用可恢复检查点加增量归档、内容去重来保留全部历史语义。不要以优化名义删除用户要求保留的版本；也不要直接删除用于重试去重的 updateId。数据库当前 223.92 MiB 不是容量危机，不能仅凭表大小认定可释放空间或直接执行 `VACUUM FULL`。

服务器可见备份目录主要包含部署文件。已检查的 systemd timer 与 root cron 中未确认到数据库定时备份任务；云控制台快照、其他用户计划任务、外部备份尚未核验，因此“是否有完整异地备份”列为待确认项，不断言完全没有备份。

## 建议实施顺序

1. 先完成完整目录迁移与本地滚动备份，保证能找回内容。
2. 增加“存储管理”页面，分开显示项目正文、媒体、可重建缓存、回收站、历史和更新包；清理前显示预计空间与保留原因。
3. 打通本地附件引用清理与云端 COS 回收队列，先只报告候选，核验后再开启自动清理。
4. 再逐步改为项目级本地存储，并对协作历史做保留内容的归档去重。

可直接设计为自动清理的对象：超额/到期的可重建预览缓存、已退出更新流程的旧安装包、确认失效的下载临时文件。项目素材、离线草稿、账号浏览器资料、旧故障备份和协作历史不进入无差别清理。

## 验证与边界

- 只读检查真实本机文件大小、结构和策略，不输出 API Key、登录令牌、云端密钥或用户剧本文字。
- 云端 SQL 在 `BEGIN READ ONLY` 事务中执行；COS 仅执行列举和配置读取，没有写入/删除请求。
- 核对四份关键后端文件与本地源码，忽略 CRLF/LF 后一致：repository-extras、director-live、media、collab。
- 72 项相关存储测试全部通过，覆盖回收站、保存顺序、迁移备份、缓存、检查点和更新包清理。测试通过说明现有约定未出错，不代表上述缺失的生命周期能力已经实现。
- 原始统计在 `output/storage-audit-local-20261011.json`、`output/storage-audit-cloud-20261011.json`；测试日志 `output/storage-audit-tests.log`。
- 本次没有发布新版本；没有为了体检改变现有保存方式或删除业务资料。
