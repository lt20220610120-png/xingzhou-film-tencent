# 导演快速模式：按时长自动分段设计

日期：2026-10-02。研究基线：`ebd40f5`，应用版本 `2.4.9`。

**当前交付是设计和实施计划，尚未修改软件、运行付费生成或发布版本。** 用户决定先理解与统筹，换执行模型后实施。第一阶段只做单场景，验收后再进入整本批处理。本文中的默认值是本次设计选择，不冒充用户逐项确认或已经完成的功能。

## 1. 目标与边界

快速模式保留现有人工 `（1）（2）（3）` 分段，增加软件内置的自动分段器：读取项目风格与画幅、最高视频时长、设定资料和整场原文，规划近似满时长的连续片段，再使用用户原有完整 Skill 生成提示词。每条在编号旁显示“建议生成时长”。

最高视频时长是 **1～30 的整数秒**，是本功能的产品范围，不代表所有视频模型都支持这些时长，也不宣称行业最长只有 30 秒。大部分非尾段靠近上限；不足上限的整场或尾段按实际需要估算，禁止拖慢、重复动作、删台词来凑时长。

不修改用户导入的 Skill，不为每种秒数新造一个 Skill，不改变总剧本、集数和场景划分，不把新逻辑接到创造模式。视频生成接口、模型能力适配和自动提交视频不在本次范围。旧的 UI、WorkBuddy 等已完成任务不与本次捆绑。

本机所选示例项目有 95 个正片分集。已有 8 条提示词平均约 3,108 个字符，最长约 4,269 个字符。因此“整场理解”应与“一次返回所有提示词”分开；整本更不能一次塞进一个生成请求。

输入分段器目前识别的是**独立行的半角/全角括号加阿拉伯数字**，例如 `(1)`、`（1）`。中文 `（一）`、正文内括号、镜头中的数值不属于本次需要扩大识别的范围。自动稿统一生成独立行 `（1）` 格式。

## 3. 用户界面与操作

### 3.1 截图中场景标题右侧

第一行使用紧凑并列控件：

`场景 1-1    分段方式 [人工分段 | 自动分段]    最高视频时长 [30 秒 ▾]`

- 老项目默认人工分段，原生成行为保持。自动模式初始上限 30 秒，可选每一个整数 1～30；选择按账号、项目记忆，键为 `xz-director-quick-settings:${accountId}:${projectId}`。
- 时长控件在自动模式启用；选定秒数不会立即收费或重排已有结果，点击现有“生成”才开始。
- 下方仍为完整 Skill 选择器及“生成”按钮，控件同高、对齐；窄屏换行，不能覆盖标题或把按钮挤成竖排文字。
- 自动模式正文区提供“原文 / 自动分段稿”两个视图。原文读取当前人工编辑稿优先，其次原场景文本。自动分段稿展示程序渲染的括号与片段内容，并在界面旁展示估计时长、衔接提示；不向原文插入这些说明。
- 在自动模式下读取已有人工括号稿时，只在生成用的副本中移除严格识别的提交标记，并重新规划。人工稿、原剧本均保留。切回人工即可使用原人工稿。
- 第一阶段自动稿只读；需要改剧情时编辑原文重新生成，需要亲自分段时切回人工。不要做可随意编辑派生稿而仍显示旧时长的伪同步编辑器。
- 生成进度：`分析整场与时长` → `已分成 N 段` → `生成提示词 k/N` → `核对衔接与完整性` → `完成`。提供“停止”和错误后的“继续未完成部分”。
- 暂存结果不混入正式提示词列表；可展开查看已生成草稿。成功后整场一次提交到正式结果。

### 3.2 提示词编号旁

`1-1-1   建议生成时长 30 秒             复制  编辑  删除`

`1-1-2   建议生成时长 10 秒             复制  编辑  删除`

时长徽标读取该条持久字段，不读当前下拉框，不用列表索引关联。提示说明：“按当前内容估算；实际生成请结合所选视频模型的可选时长。”此处是估计，不能标为测得的视频时长。

旧提示词没有时长时不补假值。用户编辑正文后保留原估计值并标记“内容已修改，时长待复核”；不得继续将其当作已验证时长。提供重新生成/重新核对入口，不静默把所有旧条目设为当前上限。

重新生成保持现有“新增结果”语义，旧结果保留并标明生成批次，便于辨认相同 `集-场-条` 的不同版本；新一轮自动分段稿切到最近成功计划。相同任务重试必须幂等，不再新增一份。第一阶段不加覆盖旧结果的隐式删除逻辑。

## 4. 时长与切点规则

### 4.1 估计模型

先理解谁在说话、对白/VO/场外声、动作、必要反应、声音与动作是否并行，再估时间。不能仅用总字数除以固定数值，也不能把并行的对白与动作时长机械相加。

模型为各段提交估计分解 `speechSeconds / actionSeconds / overlapSeconds / transitionSeconds`。估计总长明确为 `speechSeconds + actionSeconds - overlapSeconds + transitionSeconds`，所有项非负，重叠不超过声音与动作两项较小值。中文自然试读可采用约 4 字/秒作为可校准初值；这是工程估计，不是保证，情绪停顿、姓名、数字、外语和快速对白都要修正。本机 Skill 也把 3～5 字/秒描述为粗估，最终以场景表演判断为主。

`recommendedDurationSeconds = ceil(estimatedSeconds)`，取整后必须在 `1..maxDurationSeconds` 内。超过上限要重新划分，不能 `min(max, estimate)` 静默截断。内容本来只需 10 秒就建议 10 秒，不能为了高利用率硬写 30。

### 4.2 时长优先的候选区

设计常量：非尾段优先在 `[ceil(0.85 × T), T]` 秒附近选结束点。30 秒对应 26～30 秒，15 秒对应 13～15 秒。85% 是首版可校准策略，不是用户原话，不暴露为普通用户的额外设置。

在此窗口中同时比较接近上限程度和衔接质量，优先较满且自然的切点。不得为 5 秒处一个漂亮特写就舍弃 30 秒目标，也不得为了等到 34 秒的人物换话而超限。前面装得较满，末尾保留真实余量；有合适 30 秒切点的 40 秒场景应为 30+10，不能机械均分 20+20。

不足一个上限的整场作为尾段处理。较长场景最后剩余不足上限时允许短尾段；不强制所有片段等长，不自动把尾段补成满长。只有仍能使前段接近上限且有明确声画收益时才可微调边界，不为消灭尾段而全场平均摊开。

### 4.3 切点偏好与例外

在允许窗口内依次考虑：

1. 甲收句、乙接话，或说话者转到听者反应；保持声源归属。
2. 剧本已有动作的手部/道具/表情特写收尾，例如擦汗完成，下一条切其他观察对象。
3. 已有动作的自然落点、视线转移、动作匹配切；记录前段终态与后段起态，不能重做动作。
4. 长台词无法等到换人时，可用已在场听者或已有细节作画面桥，声音继续。连续原话按语义子句分配，拼起来刚好一次原话；禁止给两条都补成一整句，也不捏造听者。

允许增加的是低影响导演表达（已有动作的特写、已有角色的自然反应、观看对象转换）；不新增剧情事件、人物、道具、动机、结果或能力。新增表达存在计划的 `visualNotes`，不写回原剧本，时间也计入预算。不能借“补特写”加入 5 秒无意义停顿。

1 秒也允许选择，但若某个不可自然拆解的语音/动作无法容纳，返回“当前内容无法在该上限下自然完成，需调整分段或上限”。不能偷偷提高上限、删剧情或假称完全满足。非尾段过短、超限或不可能的容量，最多一次自动修正；仍不能解决则保留计划为待核对状态，不继续收费生成整场。

### 4.4 时间与剧情验证分层

- 程序能确定：范围、覆盖、顺序、整数建议秒数、是否超设定上限、非尾段是否落在目标窗口。
- AI 负责判断并给出可核对依据：表演时间估计、是否可以声画并行、切点与人物道具状态是否合理。
- 软件测试不能证明生成视频精确等于估计秒数，也不能保证模型绝不穿帮。发布记录和交接必须区分工程验证、真实文本试用、视频实测。

## 5. 自动路径的完整调用链

### 5.1 快照与原文带

点击生成时冻结账号、项目/分集/场景 ID、风格、画幅、设定资料、当前原文、秒数、完整 Skill 内容哈希和所选模型配置指纹。API Key 只在内存与既有安全配置中使用，不写入检查点。内容哈希用于一致性判断，不是发送给模型的内容摘要；实际 Skill 仍完整发送。

`buildSceneSourceTape` 对换行、BOM 做明确归一；只在生成副本移除严格匹配的旧括号标记，保存原文与映射。场景标题作为共享元信息，其余文字保留。正文按段落/标点形成有稳定 ID 的文本单元，程序记录原始区间，不让 AI 重写全文来“保证不遗漏”。

规划输出使用有序结束锚点：`{ unitId, prefix? }`。默认到该单元结尾；长台词必须在单元内部切分时给该单元的精确前缀，程序确认逐字匹配并落在合法文字/词语边界，换算成区间。每段起点只能是上一段终点，终段必须到全文末端。这样正文覆盖自动可证，不会重复/漏掉一段。源文本中的标题、标记与被保留正文分别有映射，不能把删除标记误算成剧情丢失。

### 5.2 A 阶段：软件内置分段规划

使用当前选定的文本模型，单独发送内置规则、项目设定、上限、设定资料及完整场景原文，要求结构化计划；没有已选模型时不能自动切到其他接口。

输出：所有分段终点、估计时间分解、起止人物/道具/光源事件状态、边界拍法、允许的导演补充及原文依据。只规划提交范围和衔接，不代替用户 Skill 输出最终提示词，不读取附件中的操作指令执行系统动作。

程序校验 schema、严格覆盖和时长规则。JSON 外围允许代码围栏；拒绝随意“修 JSON”导致数据变化或将分析文字误作结果。结构性问题最多一次携带错误清单的修正请求，保留原计划及原因。通过后渲染 `（1）…（N）` 自动稿并持久保存检查点。

### 5.3 B 阶段：完整 Skill 按段执行

**选定方案：自动路径默认串行逐条输出，完整场景始终作为参考。** 这样控制输出长度，并能延用上一条的已验证末态。不能直接复用当前 `Promise.allSettled(tasks.map(...))`。人工路径本次保持原行为。

每次消息包含：

1. 既有 `buildSkillMessages` 生成的完整主文件与所有附属文件，原样、无静默截断。
2. `beforeUserMessages` 提供只读参考：项目风格/画幅、设定和小传、整场无括号参考原文、整场分段表（使用 segment ID 与引用区间，**不呈现为提交括号**）、全部计划起止状态；从第二条起另附共用光影基调与上一条完整输出。
3. 当前 user 输入：再次置顶项目设定；明确“本次只提交下面一个括号，其他内容是整场参考”，指定规范编号、当前建议秒数及最高上限；只有当前内容使用 `（k）`，随后为精确原文和分离的导演拍法说明。

这解决 Skill 的“N 个括号输出 N 条”与分请求输出的兼容：每次真正提交一个括号，参考材料提供整场理解，不要求 Skill 忽略自己的合同。预演必须在首次输出前覆盖整场，后续不得重造摄影基准。

第一条校验通过后，提取原有“光影基调”行作为本次唯一基准，后续原样传入并逐条比较，仅允许排版空白差异。基础状态以 A 阶段计划为约束，前条实际结尾用于核对而不是覆盖剧本事实；若上一条违背计划，先修正它，不能把错误传播下去。光源变化使用 Skill 原有“光源事件”规则，不因基准固定而把熄灭的灯重新打开。

所有请求使用同一个快照模型/Skill。完整 Skill 及上下文装不下时停止并显示容量原因，不悄悄截取主文件、删后续剧情或切换模型。首版不创建一个自动摘要系统来掩盖不够的上下文；可让用户改用更大上下文的既有模型。

### 5.4 C 阶段：校验、暂存、提交

逐条确定性检查：当前请求恰好一条结果、编号正确、正文非空；已支持的 v8.2 合同检查五个区块、每镜六行、光影基调一致；从连续台词区逐句对账，不能把基础设定中的重复人名算成台词重复。台词白空格/引号排版可归一，实际字词、顺序、说话人与可听方式不得默改。

通用 Skill 只应用已声明/可识别的合同检查，不按名称猜测所有用户 Skill 都采用 v8.2 模板。首版提供应用内只读 `fast-v8` 合同适配器，以结构特征与合同指纹选择；未知结构仍走通用编号校验与原文语义核对，明确未使用专用结构检查。导入的 `check_prompt.py` 作为本次研究参考，应用不自动执行任意导入脚本，也不引入 Python 运行依赖。

全场末尾再用同一文本模型做一次只读语义核对，返回有原文/片段引用的结构化问题清单：事件遗漏/重复、状态重置、角色错认、提前透露后文、时长挤不下、衔接不成立。逐条确定性校验不能替代这一层；这一层也不冒充数学证明。长场景按相邻两条及各自来源范围分批核对，不能截断输入。成功的核对范围做检查点，重试不全部重审。

默认请求数量约为 `1 次规划 + N 次 Skill + 1 次全场核对`；超长核对会分批，错误修正另计。界面进度说明工作阶段，不预报未经证实的费用或耗时。每个失败规划/片段最多一次明确的自动质量修正；网络中断和服务端不明状态不自动无限重试。已成功片段不重新计费生成。

校验通过后一次原子应用场景结果，同时写分集与历史。如果任一片段失败，保存草稿/错误/进度，旧正式结果保持；不能像当前人工路径一样先把部分片段追加却把全场标成完成。再次继续只执行未通过部分；若前序修复改变共享基准或起止状态，依赖的后续片段/审核标为失效后再处理。

## 6. 数据与状态合同

以下为必需字段与责任，实现使用 JS/JSDoc，无须引入 TypeScript 或状态库。

```text
QuickSettings = { segmentationMode: 'manual'|'auto', maxDurationSeconds: integer 1..30 }
SceneSnapshot = {
  accountId, projectId, episodeId, sceneLabel, sourceSnapshot, sourceHash,
  settingsHash, skillId, skillHash, profileId, profileHash,
  maxDurationSeconds, style, aspectRatio, settingText, rulesVersion: 1
}
ScenePlan = {
  id, version: 1, sourceHash, sourceSnapshot, sourceText, sceneHeader, sceneLabel,
  settingsHash, skillHash, profileHash, rulesVersion, maxDurationSeconds, createdAt,
  segments: [{ id, index, sourceStart, sourceEnd,
    estimatedSeconds, recommendedDurationSeconds, timing,
    startState, endState, boundary, visualNotes }]
}
SceneRun = {
  id, snapshot, plan, phase, revision, createdAt, updatedAt,
  sharedBaseline, segmentDrafts, checks, errors,
  promptIds, commitKey, pendingRequestId
}
新增提示词字段 = {
  segmentationMode: 'auto', generationRunId, segmentationPlanId, segmentId,
  sourceHash, maxDurationSeconds, estimatedSeconds, recommendedDurationSeconds,
  durationStatus: 'estimated'|'needs-review', timingRulesVersion: 1
}
```

已有 `generationMode` 继续为 `'quick'`，不发明 `quick-auto` 破坏模式识别。`label` 仍为 `集-场-条`；run ID 在启动时分配，promptIds 在计划验证通过、确定 N 后一次分配并持久保存，不能每次恢复重新随机生成。估计秒数可为正小数，建议秒数是整数。`sourceSnapshot` 是点击时的原输入，`sourceText` 是移除提交标记及单独提取场景标题后的规范正文；`sourceStart/sourceEnd` 始终是 `sourceText` 的 JavaScript UTF-16 半开区间，边界另验 Unicode/词语完整性，不能混用原始文本偏移。

- 正式 `ScenePlan` 放入 `episode.quickScenePlans` 数组，每项有稳定 `id`；`episode.activeQuickScenePlanIds[sceneLabel]` 指向当前成功计划。原输入和规范正文各在计划存一份，片段引用区间，不把全文复制 N 次进新增元数据。旧提示词字段 `sourceText` 沿用当前片段及项目设定作为最小兼容内容，避免再次把完整 Skill/整场复制到每条。
- 完成提示词仍使用 `episode.prompts` 与 `project.promptHistory`，两处保留相同元数据。删除规则及已有墓碑保留，恢复任务不能复活用户删掉的提示词。
- 活动 `SceneRun`、部分输出、错误与检查点存在本机数据目录 `导演工作台的项目/quick-generation/<account-key>/<run-id>.json`，通过专门 IPC 访问；目录名由程序安全映射 ID，不接受模型给出的路径。采用临时文件写入+原子替换，每次成功阶段都等落盘完成。只用于当前功能，不重构全应用存储。
- 正式计划和提示词可随原有分集云同步；活动任务检查点不上传云端，不把运行中的任务交给另一台电脑自动继续。
- 运行期控制器挂在 App 生命周期，切场景、切页面不取消；退出软件后不承诺继续工作，重新打开列出中断任务，用户点击继续再调用模型。切换账号立即暂停本账号任务，旧请求回包不得写入新账号视图或另一个项目。

状态机：`planning → validating-plan → generating → auditing → ready-to-commit → completed`。旁路状态：`paused / failed / needs-review / stale / cancelled`。重启时活动状态统一转 `paused`。暂停/取消均拒绝晚到回包；保留已经产生的可用草稿，不能把取消当成功。

提交时重新比对账号、场景源哈希、风格/画幅/设定、Skill 和模型指纹；源稿被修改、场景删除/重排、云权限改变时不静默落入当前结果，置为 `stale` 并供查看/新任务重做。比对模型/Skill 时按 run 中固定的 ID 解析其当前内容，不能拿用户刚切换的下拉选择替代。用户仅在另一场景切换，或改下次任务的时长/模型/Skill 选择，不使已启动任务失效；真正修改该 Skill 文件内容或模型连接配置才触发一致性检查。API Key 轮换不写入公开模型指纹。

本地提交使用持久 outbox 思路：先保存 `ready-to-commit` 完整检查点，再以固定 promptIds/commitKey 合并最新 state，串行保存最新导演项目快照并等待确认，最后标 completed。崩溃恢复重复应用同一 commitKey 不新增提示词；不存在项目/分集不能只写历史而留下孤儿结果。全局 250ms 自动保存与显式提交共用同一顺序写入器，防止旧快照覆盖新结果；副作用不能放进 React setState updater。

两份本地正式存储确认后，completed 检查点可压缩为只含目标 ID、runId、commitKey、promptIds、指纹、状态和时间的回执，正文以正式计划/提示词为准；失败/中断草稿不得顺手清除。恢复已完成回执只确认状态，不重新请求模型或复活删除的提示词。

## 7. 编辑、历史、云同步与导出

1. 修改提示词时，正文与 `durationStatus='needs-review'` 同时写分集/历史；徽标继续展示估计但明确待复核。
2. `mergeCloudEpisodes` 合并 plan 数组按稳定 id；活动指针若同场两端有不同新计划则保留两个计划并显示冲突，不按本机时间强行选择。三方合并保留现有冲突语义。云端未返回新字段的老记录不能抹掉本地已有计划。
3. 总剧本重解析和新增分集使用纯函数进行身份映射：未变集/场可沿用，新增/删除/重排/重复标题存在歧义时留存旧计划和提示词为历史、将活动指针标失效，绝不按新数组位置套用旧分段稿。历史条目不丢失。
4. 纯“复制”保持 Skill 正文原样；不向 v8.2 输出加新的一级字段。批量导出的 `【1-1-1】` 标题保留，在正文外可写一个应用元数据行：`行舟影视时长：建议=10秒；上限=30秒；状态=估算`（待复核时状态为“待复核”）。仅新的自动记录带此行。
5. `parsePromptBook` 精确识别上述独立行并提取为条目元数据，不把它混入实际视频提示词，也不误把正文里的“30秒”当 metadata；老文档照旧。图视生成整本条目旁可显示建议时长，但首版不自动覆盖视频时长控件。模型只支持部分时长时由用户选择实际可用值。

## 8. 第二阶段：整本生成的边界

单场景完成并经用户实际试用认可后再实施。入口放在快速模式的项目层工具区，名称“一键生成整本提示词”，不伪装成当前场景的“生成”。

由 `parseDirectorScenes` 与同一套正片分集排序产生任务，排除设定和小传、空集/空场。一份任务快照固定选中的秒数、模型、Skill、项目设置，各场景独立使用第一阶段管线；**不能跨场景凑满时长**，每场都允许自己的短尾段。

默认按集、场顺序每次运行一个场景。展示总场景数、已完成/失败/跳过、当前集场、当前片段和可恢复错误。提供暂停、继续、重试失败与结束任务；整个软件关闭后待重开恢复，不宣传离线继续。

开启前的范围预览用于明确整本任务和已有结果处理：默认“只生成缺失场景”，任何已有提示词的场景保守跳过；“重新生成全部”明确保留旧结果，新生成作为新批次。另一个完整性指标指出旧场景未必完整，不能把“跳过”计为本次验证成功。中断的同一任务按检查点继续，不把未完成场景当作完整跳过。

每完成一场独立落盘，退出页面/断网不丢已完成场景；失败场景保留错误并可继续下一场，不让后续全停，但账号/权限/模型不存在、全局限流等系统性问题暂停队列。云同步由项目级串行协调器处理，不依赖用户恰好打开该项目。多个机器同时生成属于不同批次，合并不覆盖，首版不承诺跨机器任务抢占或一次且仅一次计费。

## 9. 方案选择与未采用的办法

| 方案 | 结论 |
|---|---|
| 直接修改每个 Skill，让其自己算时长分段 | 不采用；用户希望继续使用现有 Skill，且不能提供可验证的独立分段结果 |
| 按字数等份切、直接加括号、再照旧并发 | 不采用；动作与对白并行、断句、连续性和不足尾段都会出错 |
| 整本剧本一次让模型输出完 | 不采用；上下文/输出长度、失败恢复和保存粒度都不适合 |
| 内置整场规划 + 全文参考下逐段 Skill + 校验 + 原子场景提交 | 采用；复用现有 Skill 和结果格式，提供清晰检查点，后续可直接组成整本队列 |

首版不加入视频语音合成测时、外部自动剪辑、新 AI 平台或依赖。应先用代表性真实文本校准“近满时长”和衔接规则，再考虑后续测时增强。

## 10. 验收标准

| 用例 | 必须出现的结果 |
|---|---|
| 40 秒受控场景，30 秒处可切 | 30+10；两条对应正确、总原文覆盖完整 |
| 同一受控素材约 150 秒，可在 15/30 秒处切 | 上限 15 得约 10 条，上限 30 得约 5 条；不将现实剧本条数宣称为精确数学结果 |
| 30 秒上限，5 秒特写、29 秒换话 | 不在 5 秒断；选接近上限的有效边界 |
| 全场只有约 8 秒，上限 30 | 一条约 8 秒，无补戏/拖时 |
| 长独白跨边界 | 台词逐字拼回且只出现一次；反应/细节桥不捏造人物；声源不换人 |
| 同场抱人、持物、受伤、灯熄灭 | 后条起态延续；摄影基准一致，灯灭事件不被复原 |
| 老手工括号稿和旧提示词 | 人工路径不被改写；旧条目不出现假 30 秒 |
| 结果漏条、多条、错编号、空输出、截断 | 不发布为完整场景；有限修正或保留可继续的错误 |
| 输入 0、31、小数、NaN，或 1 秒不可容纳事件 | 非法值拒绝；真实容量问题可见，不自动调上限 |
| 生成时改原文/删场景/切账号 | 无覆盖、无串写；草稿可查、状态可解释 |
| 第 3 条失败、重启再继续 | 前 2 条复用，最终只保存一套本轮记录 |
| 保存后云刷新、退出重开、历史导出再导入 | 编号、分段范围、建议时长和修改状态不丢不串 |
| 总剧本插入/删除/重排/重名分集 | 不按旧位置错绑计划；旧提示词与历史保留 |

第一阶段工程门槛：行为测试通过、全量 `npm test`、`npm run build`、模拟接口的真实 UI 交互验证通过、按 AGENTS 发布并核验更新清单。质量门槛：用户在已发布单场景版本上使用自己的模型测试对白、动作、短场景/尾段，并认可结果后，才开始第二阶段。模拟测试只证明工程逻辑，不能代替真实提示词质量验收。
