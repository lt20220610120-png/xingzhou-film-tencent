# 视频生成前素材关联：现状复现、GitHub 调研与改进方案

日期：2026-10-20

状态：本文记录原架构研究与问题诊断。随后经用户授权实现前置关联本机试用包，验收见 `docs/release-verification-2.8.54-private.1.md`；本文复现结果仍指修复前基线。
基线：行舟影视 `tencent/` 2.8.53，提交 `125778d`。

## 1. 本轮问题的准确界定

用户指出：美术清单核实无误时，同场素材通常已经齐全；下游主要问题是本条携带了只属于同场其他条目的素材，以及 `@` 没有准确绑定。人物所有的物件有时在人名优先的命名下被误关联成人物。

本方案据此把主任务明确为：

**在正确的同场候选素材中，按本条实际画面选择必要子集，并把提示词中的实体准确绑定到所选具体图片。**

不把“AI 自动补大量新素材”作为默认流程。还要区分：

- 素材存在，但本条没被程序识别或没有插入 `@`：属于关联问题。
- 素材存在，但类别/身份在导出导入时丢失：属于数据传递问题。
- 素材有记录，但图片缺失、下载失败或版本不合适：属于资产可用性问题。
- 原清单确实漏了本条必需资产：才回到美术核实环节补充。

前三种不能统称“美术漏做”，更不能自动重新出图掩盖问题。

## 2. 结论

用户随后提出把关联提前到清单核实与美术卡片阶段。已补充[提示词与美术卡片提前关联：可选新模式设计](2026-10-20-prompt-art-prebinding-design.md)，作为下一阶段优先方向：已有提示词只读使用，先绑定卡片，再连接选定图片，最终编译引用。保留旧模式，先本机试用。本文现状诊断继续有效；后面的 P0/P1 能力将先在这个前置关联模式中贯通。

**用户提出“道具本体在前、所属人物在后”是合理的命名方向，但仅靠改名不足以解决现有问题。**

已通过隔离的函数调用和真实导出/导入函数复现一条完整错误链：

`美术资产有 prop 类别 → 导出只写图片文件 → 导入仅重建文件引用 → category/assetId/imageId 丢失 → 匹配把“张三-杯子”截为“张三” → 杯子插入人物 @ 引用`

因此即使上游分类正确，下游也可能错绑。本轮没有读取用户反馈的真实错误项目，不能说所有用户案例都由这条链引起；但该路径在当前源码下可以确定复现。

最优先应解决“数据身份丢失、跨类型短名匹配、已选素材与候选素材混用”，再接 Agent 的语义判断。不应让大模型每次从几个含糊文件名重新猜一遍。

## 3. 证据与复现

诊断脚本：`docs/superpowers/validation/2026-10-20-reference-binding-probe.mjs`。
本轮报告：`output/reference-binding-research-20261020/probe-n1jaoP/report.json`。

运行方式：

```powershell
node docs/superpowers/validation/2026-10-20-reference-binding-probe.mjs
```

它直接导入当前生产模块，使用虚构人物和一个像素的图片夹具，在独立 output 子目录操作。没有真实人物资料、用户项目、模型请求或付费调用。10 个函数场景和 1 个文件往返场景已完成；断言确认的是**当前问题与对照行为**，不是修复后的通过结果。

### 3.1 复现结果

| 场景 | 实际结果 | 说明 |
|---|---|---|
| 无类别的“张三-杯子”，人物写张三，道具写杯子 | 人物张三被插入人物图及杯子图两个引用 | 可复现错绑 |
| 相同名字，但明确保留 category=prop | 杯子不会再绑到人物；仍未对应到简写“杯子” | 类别能挡错绑，但不能独自解决别名 |
| “张三的杯子”，不含横线 | 没有误绑人物，但简写“杯子”也没匹配上 | 不能笼统说所有人名前缀都必然错绑 |
| 改为“杯子-张三”“杯子-李四”，提示词只写杯子 | 两个杯子一起绑定 | 本体在前仍需分辨具体是哪一只 |
| 五个人用顿号连接 | 此虚构格式下没有自动插入人物引用 | 把组合文本当一个主体 |
| 五个人用逗号连接 | 只给第一个人插入引用 | 逗号被当作人物描述起点 |
| 相同五个人用分号连接 | 五个人分别绑定 | 正常对照，证明受格式影响 |
| 张三穿白衣，候选有白衣和黑衣两套 | 两套同时绑定 | 没有按当前状态做唯一选择 |
| 已挂载张三、李四、杯子，本条只需张三 | 李四和杯子仍留在 references | 未插入 `@` 不等于不发送素材 |
| 张三原先误写“参考@image2”，image2 是杯子 | 错误引用保留，并追加正确人物引用 | 当前自动匹配倾向保留已有手动内容 |
| 有 category=prop 的杯子经实际导出/导入 | 导入无 category、assetId、imageId，杯子随后绑到人物 | 完整链路确认 |

上述五人用例以空 references、独立 candidates 测量“自动找出并插入引用”的能力。在实际整本导入流程中，素材往往早已全部挂载，所以即使少插入 `@`，图片仍可能全数提交。这正是需要分开检查“选中哪些图片”和“引用指向哪里”的原因。

### 3.3 已有测试为什么没有挡住

运行了 `automaticReferences.test.js`、`generationReferences.test.js`、`storyboardReferences.test.js`，共 **23/23 通过**。

现有测试部分明确要求同名多图全部关联、保留原 references 和手动别名。这些行为方便人工操作，但不等于满足无人值守的精确选择。因此新自动化要求需要新的绑定规则与验收标准，不能用“原有测试全过”证明关联足够准确。

## 4. 改进一：美术命名与结构化身份

### 4.1 采纳本体优先，但不让名字承载全部事实

建议展示：

- 人物：`张三｜白衣常服`
- 道具：`杯子｜张三常用｜白瓷｜完好`
- 道具：`杯子｜李四常用｜玻璃｜完好`
- 场景：`客厅｜张三家｜日`

这是界面展示，不要求用户手动记 ID；也不是要求马上把旧文件全改成这个格式。程序依据独立字段识别：

| 字段 | 示例 | 含义 |
|---|---|---|
| entityId | prop-cup-01 | 同一物件的稳定身份 |
| category | prop | 道具类别，不随名字变化 |
| canonicalName | 杯子 | 物件本体名 |
| displayName | 杯子｜张三常用｜白瓷 | 供人阅读 |
| aliases | 张三的杯子、那只白瓷杯 | 有依据的别名，不能全局随意映射 |
| ownerEntityId | character-zhang | 所属关系 |
| variantId / state | intact | 当前可见状态，必要时区分破损等 |
| imageId / imageRevision | image-cup-01 / 2 | 选中的具体图片版本 |

**所有者与当前持有人不同。** 张三把杯子交给李四，不应新生成“李四杯子”或改变道具身份；用条目中的 `heldBy` 关系表达。只有具备独立视觉价值的物件变化才建立状态差异，沿用现有美术原则。

泛称“杯子”有两只候选时，Agent 根据动作、归属、连续性和外观判定；无足够证据则不自动挑第一张。不能把“杯子”永久登记成两只杯子的无条件别名。

### 4.2 图像本身也要核对

名字和 category 正确，不证明图片确实画对。美术出图后对图片做一次有记录的视觉核实：主体是否符合资产类型、指定颜色/形制是否符合、是否混入不需要的人物或场景。结果按图片哈希缓存，换图后失效。

不能简单以“出现一张脸”判为人物：相框、雕像、拟人道具、人物定妆的多视图都可能有例外。冲突送资产核实，不让视觉模型静默改已确认分类。

## 5. 改进二：导出导入不能丢身份

### 5.1 软件内部直连优先

在行舟内部把导演条目与协作资产传给自动化时，直接按 ID 读取快照，避免必须先导出图片再根据文件名还原。用户原有文件夹工作法继续支持。

### 5.2 文件夹附带资产清单

每次按场导出，图片旁附 `assets-manifest.json`，保存：

`schemaVersion, projectId, sceneId, assetId, entityId, category, variantId, imageId, imageRevision, relativePath, sha256, displayName, aliases, ownerEntityId`

导入验证文件存在、路径在选定根目录内、哈希一致、身份不冲突。按实际清单还原分类和版本，不从人名猜类别。外来清单是数据，仍需核验，不能因为有 JSON 就全部相信。

文件内容可按哈希去重，但两个语义资产碰巧共用同一图片时，不能把它们的资产身份也合并。一个文件可以被多个明确的资产引用。

### 5.3 兼容旧素材

旧文件夹没有清单时：先尝试从当前项目资产及内容哈希找回身份；找不回才由 Agent 结合命名、上下文、图片给出建议。未知类别须标为未知，不能自动放宽成人物/道具都可匹配。

旧项目改展示名时保留 assetId、imageId、原名别名、已核实的场关联和人工排除；不重复出图、不批量重建资产。涉及名字键的旧合并逻辑需有迁移预览和回归覆盖。

## 6. 改进三：每条提示词保存明确的素材需求

### 6.1 三个集合分开

1. **同场候选素材**：这场可以用什么。
2. **本条选用素材**：本条实际要提交什么。
3. **提示词引用映射**：文本中的人物/道具/场景分别指向哪张图。

“从本条删除”只改变第二、第三集合，不删除同场素材或影响第二条、第三条，也不删除磁盘图片。

### 6.2 Agent 输出结构化决定

每条生成需求表：

```text
entryId / promptRevision / sceneRevision / assetCatalogRevision
requirements:
  entityId
  category
  variantId
  imageId
  role: identity / environment / prop / first_frame / last_frame / style / continuity
  presence: on_screen / off_screen_voice / mentioned / absent / uncertain
  evidence: 原文位置、提示词位置，或明确的连续性依据
decisions:
  保留 / 从本条排除 / 待确认
  原因、是否人工锁定、检查状态
```

Agent 必须检查本条整段的所有子镜头，而不只是第一句或第一帧。比如 15 秒提示词包含三个子镜头，杯子只在最后 3 秒出现，仍可能需要保留；不能误当作属于下一条而删去。

上下条用于解读“他”“递过去”“仍穿原来的衣服”和道具传递，不把上下条所有出现对象都加入本条。

“画外音”“仅对白提及”“人物离开后已不入镜”等通常不需要人物画面参考；必要的音色参考独立处理。场景参考也可能用于局部镜头的空间一致性，不能只看场景名称是否逐字出现在提示词中。

一个角色默认选当前明确妆造和图片版本；确需正面/背面等多图，应有同一身份的多视图组与用途记录，不再默认把同名全部图片一并提交。

### 6.3 在现有工作流中的位置

用户现有顺序是先提示词、后美术。无需为了绑定强制重排工作流：

- 生成提示词时同步提取语义需求和原文出处；此时没有资产 ID 也可先保留角色实体、道具本体及状态。
- 美术核实完成后，把语义需求解析为已存在的资产/图片 ID。
- 进入图视生成时自动形成每条的选择及 `@` 映射。
- 半自动用户已确认的选择作为锁定快照；Agent 做一致性检查，发现冲突提出修改，不静默覆盖。

新旧文本格式都需要支持；不强制用户把所有逗号改成分号。直接无条件按逗号拆也不合适，因为“张三，穿白衣，手持杯子”含人物描述；采用结构化主体列表，旧文本由 AI 结合上下文抽取并检验。

## 7. 改进四：最后再生成 @，提交前验证实际请求

流程：

`本条语义需求 → 限定类别和身份 → 唯一资产/图片版本 → 冻结选用清单及顺序 → 编译 @imageN → 协议转换 → 实际请求核验`

`@image1` 是最终请求中的序号，不是长期资产身份。稳定身份存在绑定表里；删除第 2 张图片后，其他引用要按身份重新编译，不能让旧的数字指向另一人。

若提示词已有数字引用：

- 有历史映射，先还原它所指的图片身份，再对新顺序编译。
- 无历史映射或与人物/道具类别冲突，进入检查；不能只追加一个正确引用而保留旧错误引用。
- 人工明确锁定但语义检查报错，提示冲突，不自动覆盖。

提交前设硬性检查：

1. 本条每个必需实体都已解释：绑定、无需画面参考，或待确认；不能悄悄漏一个人。
2. 每个自动选入图片都有明确用途；未选同场候选不进入请求。无需出现在正文的首尾帧/风格参考需明确角色，不以“没 @ 就删”一刀切。
3. 人物引用不会指向 prop/scene；道具绑定不能因 owner 指向人物图。类别未知不能自动放行。
4. 每个 `@` 均能指向真实上传位置，无悬空编号；别名转换后仍对应同一图片哈希。
5. 两个杯子、两套衣服等歧义不能按列表先后来决定。
6. 引用数量和参考用途满足所选模型；达到上限时提出分段/调整，不静默删除关键人物或道具。
7. 校验输入快照未过期；提示词、妆造、图片、选择、模型任一影响关联的变化，都使对应检查失效。
8. 软件最终提交对象与已审定绑定快照完全一致，禁止其他自动匹配函数在提交时又把排除项加回。

不同视频模型不一定原生理解同一套 `@imageN`。适配器必须明确其引用语法、数组顺序、首尾帧/多图能力；测试真实发送结构，不能只看界面上的引用标记。

预检只保证输入绑定可追溯，不能保证生成模型一定忠实执行。下游视频检查仍保留，但第一道重点放在付费之前。

| [GLiNER2](https://github.com/fastino-ai/GLiNER2) | 支持实体、关系、结构化字段抽取，提供多语言模型路线 | 可选本地候选提取器，把“人”“物件”“所有者”分开 | 必须在中文短剧、名字、简称和隐含动作上实测；不以 README 声称的能力当本项目准确率 |
| [OpenCLIP](https://github.com/mlfoundations/open_clip) | 图文编码和相似度基础 | 可选辅助发现“标为杯子却像人物”的离群图、候选排序 | 相似度不能证明这是谁的杯子，不能单独判定身份/动作或决定是否入镜 |
| [LocalMiniDrama 文档](https://github.com/xuanyustudio/LocalMiniDrama/blob/main/docs/en.md) | 明确多图引用槽位与场景/人物/道具排列关系 | 参考“槽位顺序是协议”的做法，增加发送前预览 | 本轮读取文档，源码树请求遇 GitHub 限流，未核实完整实现；不能声称更准确 |

最值得优先吸收的是**明确的条目绑定关系、原文证据和最终引用编译**。没有查到已验证能直接保证本项目“所有素材永远无错”的现成组件；也没有必要为这个问题先更换整套短剧平台。

## 9. 推荐实施优先级

本轮仍是方案，不进入实现或发布。架构审定后建议：

### P0：先堵住可确定的错绑

- 资产类别、ID、图片版本贯穿内部传递和导出导入。
- 停止跨类型使用横线前缀推断人物；未知类别走识别/确认流程。
- 区分候选与本条选用，保留人工排除和锁定。
- 自动化的旧引用冲突、悬空引用和实际请求身份不一致一律拦截。
- 不把同名多图全部关联作为自动化默认。

这些应在自动化首次付费提交之前完成，不拖到全自动前半段的最后阶段。

### P1：让 Agent 代替逐条删图、补 @

- 每条生成“入镜实体—具体形象—所选图片—原文依据”的绑定表。
- 检查完整条目及前后文，处理五人列表、代词、画外音、交接道具。
- 按用户已选策略有限修正；仍不确定暂停受影响条目。
- 以矩阵展示本场素材在每条的保留/排除，人工只审少量疑问。

### P2：改善源头和历史兼容

- 新美术命名用本体优先，所有者和状态存独立字段。
- 旧资产渐进映射身份和别名，避免全库重命名破坏复用。
- 美术图视觉校验、真实用户样本评估，再决定是否引入 GLiNER2/OpenCLIP 等额外组件。

P2 的命名规范可与 P0 同时补入新项目规则；“历史迁移和额外模型引入”放后，避免修一个绑定问题牵动全部旧数据。

## 10. 展示给用户的核对形式

例如同场四条提示词：

| 素材 | 第1条 | 第2条 | 第3条 | 第4条 |
|---|---|---|---|---|
| 张三｜白衣 | 保留 | 保留 | 排除：已离场 | 排除 |
| 李四｜常服 | 保留 | 排除：仅画外音 | 保留 | 保留 |
| 杯子｜张三常用 | 排除：本条未用 | 保留：拿起杯子 | 保留：交给李四 | 排除 |
| 客厅｜日 | 环境参考 | 环境参考 | 环境参考 | 环境参考 |

这只是虚构说明，不是用户已确认剧本。点选任何格子可看到对应提示词/原文证据、具体图片，以及最终 `@` 指向。允许一键应用高确定项，疑问项单独核对；全自动按既定策略完成同样的检查。

## 11. 验收要测什么

建立用户认可的代表性“场景—多条提示词—全场资产”样本集，分别标注：

- 候选库是否完整，哪些问题属于上游。
- 每条该保留/排除哪些实体、状态和图片。
- 各人物/道具引用的正确图片及角色。
- 哪些情况信息确实不足，正确动作就是待确认。

必须覆盖本轮所有复现、人物称谓/别名、五人同框、同名多图、不同妆造、仅提及人物、画外音、物件交接、同一条多子镜头、局部环境参考、旧文件夹、重排删图、换模型和重启恢复。

分别统计：错绑率、多选率、漏选率、歧义拦截率、人工处理比例、修正成本。不能用“把所有素材都选上”换取低漏选，也不能把“全部暂停”当高准确。

工程验收要求：已知跨类型错误、缺失身份、悬空 @、过期绑定和超限关键素材不自动放行；每次提交都有与实际请求一致的清单。语义质量用人工标注评估，不先宣称未经测量的准确率。
