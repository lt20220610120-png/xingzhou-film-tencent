# v2.4.14 自动分段修正

本次规则来自用户对 2-1 场 15 秒模式、4-5 场 30 秒模式的实测反馈。对照原始任务与原文后，确认前者由程序逐词填满片段造成，后者还存在系统台词中“主线任务：”被误识别为说话人的问题。原始任务、正式结果与用户剧本均保留。

## 完整台词优先

- 一次讲话按原文可听字数、约 4 字/秒估算。能在单条上限内说完的整次讲话必须留在同一条，放不下时整体移到下一条；即使讲话里有多个句号，也不为凑时长拆开。
- 一次讲话本身超过单条上限时，允许在完整句号、问号或叹号后继续到下一条。逗号、词语边界、Unicode 字符边界均不能单独证明它是合理的台词断点。
- 说话人姓名、OS/VO、括号语气、冒号以及首个口播字属于同一块，不能在头部中间切分。
- 非尾段接近 85% 上限仍是常规目标。当当前段加上下一完整讲话会超出上限时，允许短于 85%，并记录 `completeDialoguePriority`。校验和正式保存都重新根据原文判断，不能靠这个布尔标记放行半句。

原始 2-1 任务第三条止于“现在这个危险的”，第四条只有“情况，先活过这七天再说。”。回归后第三条止于系统完整台词，第四条包含“现在这个危险的情况，先活过这七天再说。”完整原句，约 4.25 秒、建议 5 秒。整场原文仍按 UTF-16 偏移连续覆盖一次，原文 `prefix` 必须逐字匹配。

## 30 秒目标的整场紧凑合并

用户明确允许：最高时长设置为 30 秒、整场自然预演超过 30 秒但不超过 35 秒时，合并为一条、用紧凑节奏生成 30 秒视频。此例外不扩展到 15 秒模式、不扩展到多条计划中的某一条，也不扩展到超过 35 秒的整场。

程序保留自然分解 `timing`，正式计划与提示词分别记录：

```json
{
  "estimatedSeconds": 30,
  "recommendedDurationSeconds": 30,
  "naturalEstimatedSeconds": 32.5,
  "durationCompression": {
    "version": 1,
    "kind": "whole-scene-30-second-fast-pace",
    "targetDurationSeconds": 30,
    "naturalEstimatedSeconds": 32.5,
    "paceFactor": 1.0833
  }
}
```

`estimatedSeconds` 在此表示经明确压缩的目标值；`naturalEstimatedSeconds` 单独保留约 4 字/秒和真实动作重叠后的自然预演时长。校验和保存再次验证全场覆盖、单条、30 秒上限、自然分解总和以及 30～35 秒区间，拒绝伪造/不一致的压缩标记。Skill 输入明确给出压缩节奏，不能删原台词、重复台词或新增填充表演。

4-5 原文的完整可听台词为 130 字，约 32.5 秒。“仓库中央的陈设”“藏在屋顶上方”是现有环境/状态，不额外加空镜；摔钞票、抓起枪、攥拳退离可以和紧邻对白/OS 同步呈现。对照真实失败原文回归后生成计划为一条目标 30 秒，自然预演 32.5 秒。明确长距离、等待、持续时长及未知复杂动作仍保留独立估算；未将所有未知动作归零。普通 40 秒整场仍是 30+10。

## 验证范围

`core/directorSegmentation.v2414.fixtures.json` 保存用户反馈场景的纯原文，不含账号或凭据。回归测试覆盖实际断句计划修复、头部原子性、长短讲话边界、30/35 秒边界、15 秒不适用压缩、40 秒正常分段、元数据正式保存及伪造标记拒绝。原有短场景、动作并行、无台词空景、未知长动作测试继续通过。

新规则不改变项目/Skill/模型快照指纹；控制器通过处理版本升级重审旧草稿，对分区变化分配新计划和提示词 ID，同时保留旧计划、付费输出与正式历史。

## 整场导演预演与一次提交

用户提供的 `video-prompt-fast-v8.2` 六个文件，与应用里已导入的同名 Skill 一致。它要求在第一条输出之前完成覆盖所有括号的整场导演预演。此前“单条生成时附带整场参考”的调用方式没有完整执行这一工作流，现改为：

1. 软件按上述时长与完整台词规则生成整场括号稿，并列明全部规范编号和各条建议时长。
2. 一次 Skill 请求包含整个括号稿、完整 Skill 附件、项目风格和画幅。Agent 先排完全部镜头、人物状态、道具和声音接续，再输出本场全部提示词；人工分段也按同样方式一次提交整场。
3. 整场原始回包先保存到断点，再按编号拆成结果卡，逐条验证和保存。软件中的逐条校验不再触发逐条 Skill 调用。
4. 输出有缺条或需要修正时，修复请求仍提交整场括号稿、全部已有输出及具体问题，保留已接受结果。停止、失败或重启后，优先处理已保存回包；不因重新打开场景就重新消费整场生成。

场景是整本并发的任务单位；同一个场景通过一次整场生成完成，各场之间可以同时运行。原 Skill 文件不作修改。
