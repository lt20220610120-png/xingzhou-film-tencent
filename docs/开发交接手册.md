# 行舟影视开发交接手册

> 写给之后接手本项目的开发者或编程助手。交接的目的，是让接手者能沿着现有产品和代码脉络快速定位，只改用户指定的功能并保护已经正常工作的部分；不是从零重新理解项目，也不是借小需求顺手重做整个系统。本文是项目入口和交接方法，不代替代码、测试、发布验收记录或用户当下的明确要求。开始任务时先核对实际仓库状态；本文中的版本、分支和目录状态是 2026-10-16 的快照。

## 1. 一分钟了解项目

行舟影视（腾讯云版）是 Windows 桌面创作软件，主要服务于短剧/IP创作和 AI 影像制作。它包含剧本创作、项目资料、导演分场与提示词、美术和视频生成、画布、项目协作、账号及云端存储等能力。用户既有项目、生成结果和协作状态都很重要；修改时要先辨明数据所有权、来源和恢复路径。

技术栈：Electron 主进程 + React/Vite 界面，Node.js 云端 API，PostgreSQL 保存账号和业务元数据，腾讯云 COS 保存媒体。应用的内容创作主要在本地，显式协作功能使用云端。AI请求可能将本次需要的文本或媒体发给用户配置的第三方服务。

本软件代码在工作区的 `tencent/`，它是独立 Git 仓库。工作区根目录不是软件仓库；那里还放着故事创作工作台、研究/原型、模拟项目及上级工作区约定。不要把这些材料误认为行舟影视客户端源码。

## 2. 接手时先核对当前事实

每次任务开始都从事实重新建立上下文，不要仅依赖旧聊天或本手册中的快照：

1. 阅读工作区根目录 `AGENTS.md`、`tencent/AGENTS.md` 和 `tencent/README.md`。
2. 进入 `tencent/` 检查 `git status --short --branch`、当前提交、与目标基线的差异、远端及当前分支。不要覆盖或清理不属于本次任务的改动、未跟踪文件、用户数据或其他 worktree。
3. 对照 `package.json` 版本、最近代码提交、`release-notes/`、`docs/release-verification-*.md`、工作区根目录 `软件更新记忆.md`、公开 Release 和两份公开更新清单。分别记录“正在开发的代码”“已发布版本”和“正在使用的软件版本”。
4. 读与本任务最接近的实现、测试和近期验收记录。若资料之间冲突，以当前代码、用户本次指令和最近的可核实发布/部署证据为准，并记录冲突。
5. 先判断请求是客户端、云端、发布、故事创作还是工作区其他任务。只有软件开发任务才按 `tencent/AGENTS.md` 工作；故事创作另遵从工作区入口约定和 `story-workbench/xingzhou-screenwriter/SKILL.md`。

### 关键功能域

- 创作和项目资料：创作工作区、剧本库、分集/大纲、IP改编、文档导入导出及本地保存。
- 导演工作台：场景/镜头拆分、提示词与 Skill、自动/人工模式、AI计划和草稿恢复、生成结果持久化。
- 美术与媒体：角色/场景资产、首次形象和参考关系、图片/视频提供方、生成任务、预览和下载。
- 协作：项目成员、云端版本、手动上传/冲突处理、审批/核实与云媒体。
- 桌面集成：模型/API设置、浏览器类工具、画布、更新器及可选外部工具。

这些域跨越多个目录；改功能前用 `rg` 搜索用户可见文案、IPC channel、数据字段和对应测试，沿完整调用链追踪，不要只依据文件夹名字改动。

### 从用户需求定位到代码

先将用户的话还原为一个具体行为：哪个页面、什么输入/操作、现在发生什么、期望变成什么、哪些现有行为要维持。然后沿下表定位。很多功能有多个变体（本地/云端、单场/整集、单图/整本、自动/手动），先确定用户说的是哪一条。

| 需求表现 | 优先检查的链路 |
| --- | --- |
| 页面布局、按钮、编辑交互 | `src/App.jsx` 与 `src/components/` → `src/*.css` → 对应 UI 回归测试。确认是不是共用组件，避免修一个页面影响所有同类页面。 |
| 本地项目/剧本保存、导入导出 | `src/App.jsx` 的状态和保存调用 → `electron/preload.cjs` 暴露的 `window.xingzhou` → `electron/main.cjs` 对应 IPC → `core/` 或 `electron/creator-documents.cjs` → 对应持久化测试。核对是否同时影响主状态和导演项目文件。 |
| 导演分场、生成计划、续跑/恢复 | `core/` 中导演生成/规划/恢复模块及其 `.test.js` → `src/App.jsx` 对应入口 → `electron/director-quick-checkpoints.cjs` 或生成服务 → 导演专项回归。2.8.31 的当前契约先读 `docs/release-verification-2.8.31.md`。 |
| 美术资产、角色参考、核实或发布 | `core/art*.js`、`core/assetImageRecovery.js` 等域逻辑 → 对应 `electron/` IPC/服务 → 页面和持久化测试；协作版本还要追 `cloud-backend/src/`。先读对应 release verification，资产身份/引用/审批往往跨多个步骤。 |
| AI/图片/视频提供方和模型配置 | `electron/ai-service.cjs`、`electron/media-service.cjs`、`electron/*provider*` / `*client*` / `model-discovery.cjs` → 设置页/生成入口 → provider 专项测试。检查模型能力和参数是否随配置保存；用模拟接口验证，避免真实付费调用。 |
| 云协作、权限、冲突、版本恢复 | renderer `window.xingzhou` 调用 → `electron/preload.cjs` → `electron/main.cjs` IPC → `electron/collab-service.cjs` → `cloud-backend/src/` API/仓储 → 数据库结构与迁移。客户端和服务端都要检查授权、幂等、冲突和旧客户端兼容。 |
| 更新、下载和安装 | `electron/update-*.cjs`、`scripts/sign-update.cjs`、`scripts/publish_release.py`、`latest.json` 生成和 release verification；必须核对安装包、签名、哈希、两个更新仓库及备用源。 |

`electron/preload.cjs` 是 renderer 能调用的桌面能力目录；新增 IPC 通常要同时有 preload 白名单暴露、main 注册、调用端和输入校验。不要在 renderer 里直接绕过它去访问文件系统、密钥或任意 Node 能力。`electron/main.cjs` 聚合了很多服务与 handler，修改前查看对应 handler 调用的服务模块和测试，不要把新业务逻辑继续堆进主入口。

### “只改需要改的地方”具体怎么做

1. 建立当前行为证据：复现页面流程、读对应实现和测试，查看现有数据形状/历史版本兼容，再用简短的话写清楚“本次改什么”和“明确保持什么”。
2. 找最小完整链路，而不是只改最显眼的 UI，也不是先做全局重构。若根因落在共享逻辑，就修共享逻辑，但用回归确认其他调用方未变坏。
3. 优先复用项目当前状态模型、服务、权限和恢复机制。用户已经依赖的保存位置、对象 ID、版本编号、API 契约、历史记录和未完成任务，都视作兼容约束，除非需求明确授权改变。
4. 为目标行为添加/调整窄范围回归；同时运行受影响模块测试。界面行为再走页面交互；发布时按正式全量流程。检查 diff 确认没有无关格式化、大范围重命名、依赖升级、数据迁移或产物混入。
5. 汇报改动的准确范围和验证证据；将新的行为约束写入相应测试和文档。不要要求用户替接手者重新讲一遍仓库已有的事实。

## 4. 用户偏好与不可丢的工程约定

详细规则在 `tencent/AGENTS.md`，它优先于本节的摘要。核心约定：

- 软件反馈通常授权直接完成架构、实现、验证并发布；只有用户明确说“只做架构/方案、不更新软件”才停在设计阶段。不要重复要求用户确认日常实施计划。
- 每次软件更新都发布新版本：更新 `package.json` 版本、`release-notes/<版本>.md`，完成测试和构建，运行时验证安装包，发布 GitHub Release 并核对两个公开更新清单及备用源。完成后更新工作区根目录 `软件更新记忆.md`。
- 最终回复必须附本次公开安装包下载链接；若本机安装包仍存在，也附可点击的本地链接。不能只告诉用户去软件内更新。
- 默认 `npm run release`。如果对应版本安装包已打包并验证，可按约定发布现有安装包；同版本不得误传别的包。
- 不记录、展示或提交 API Key、云端密钥、GitHub 凭据、账号凭据。密钥只留在服务器 Secret/本机安全存储。
- 不以绕过产品权限检查的方式修复权限错误。云端改动先准备备份/回滚，再小范围部署并检查健康状态；数据库迁移需单独审慎核对。
- 保留已有用户资料。测试优先使用副本、fixture 和模拟接口；除非用户明确要求，不调用付费生成、不修改真实项目、不代用户发布真实内容。
- UI 更新要实际验证交互。用户明确表示不使用 `frontend-design` Skill，视觉取舍依据用户截图、可读性和真实界面表现。
- 发布完成需做独立复核。最终说明改了什么、验证了什么、发布到哪里及剩余限制。

## 5. 开发和验证

从 `tencent/` 运行：

```powershell
npm install
npm test
npm run build
npm run dev
```

按任务选必要验证；全量测试和构建由正式发布流程执行。`npm test` 经 `scripts/test.cjs` 聚合运行 `core/`、`electron/`、`cloud-backend/test/` 下的测试。界面变化还要做实际页面交互检查；安装与更新变化要运行打包安装程序或对应安装包检查。涉及云端部署时，必须区分本地 mock/只读验证与真实服务器操作并在记录中写明。

正式版本按 `tencent/AGENTS.md` 执行 `npm run release`：测试 → Vite 构建 → Windows NSIS 安装包 → 安装包运行验证 → GitHub 发布 → 两个更新仓库写入签名 `latest.json` → 官方备用源发布/验证。发布凭据使用本机 Git credential 或安全环境变量，不输出值。若网络中断，先查询 Release asset、两份清单和文件哈希后再重试，避免重复上传或覆盖错误资产。

## 6. 数据、安全与回归保护

- 本地业务资料和云协作项目不是一回事；不要把“本地保存”悄悄改成“自动上传云端”，也不要在未理解数据流时做批量迁移。
- 对恢复、删除、冲突解决、换目录、媒体引用、版本发布和付费任务，先追踪状态机和幂等键，再改实现。失败恢复必须保留用户原稿、已有任务/作品和必要历史。
- 以项目副本验证改写、重排、计划合并等功能。删除、覆盖或恢复操作应有明确范围、权限校验和可回退证据。
- IPC 输入要验证调用者、参数和路径；不要把主进程能力无条件暴露给 renderer。云端授权不可仅靠 UI 隐藏控件。
- 成本型生成测试使用模拟接口。测试断言要验证实际请求次数、持久化结果和错误恢复，而不只是按钮文案。
- 存储清理不能依据“文件老/没有明显引用”就直接删。参考 `docs/storage-health-audit-2026-10-11.md` 的局限说明；任何真实清理需重新只读盘点、证明引用关系并有恢复期。

文档有时是某次审计的时点结论，先读开头的范围、日期和限制。若历史资料与现在行为冲突，做新的复核并在本次记录中注明，不要静默改写过去的事实。

## 8. 每次任务如何把经验交给下一位

1. 开始前记录本次基线：版本、分支、提交、未提交/未跟踪项，以及用户要求的范围。
2. 改代码时补充可读的回归测试；记录关键数据流、边界条件、决策依据和未解决问题。
3. 完成后写/更新对应主题文档和发布验收记录，明确实际验证范围、mock 与真实环境边界、结果和剩余限制。
4. 发布后同步更新版本说明、更新记忆、下载链接和哈希；把本手册中会影响下一位接手者的状态、入口或规则更新到最新。
5. 不将猜测写成事实，不把 AI 建议写成用户确认，不把本机快照写成所有用户状态。不要把秘密或用户项目正文复制进通用交接文档。

下一位开发者可把本手册作为上下文入口，再附上这次具体需求。若要让新工具掌握当前工作，不必把整段旧聊天都喂给它：交付本手册、完整 `tencent/` 仓库和与该需求相关的最新验收/设计文档，并要求它先按第 2 节核实工作树。
